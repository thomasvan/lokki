# The live pair: relay :8381, cliproxy :8318

The relay on `:8381` sits in front of the cliproxy container on `:8318`. This page is what runs, how it is kept running, and how
to change it. How the relay behaves is in [`relay-8371.md`](relay-8371.md) (the name is the earlier port; the behaviour is the same
code); what a cut costs is in [`cost-of-a-cut.md`](cost-of-a-cut.md).

```
client (Codex CLI)
  -> relay 127.0.0.1:8381, <tailscale-addr>:8381     container relay-8381 (host network), image built from main: docker.md
  -> cliproxy <tailscale-addr>:8318                  container cli-proxy-api-8318 (listens on 8317 inside), compose, image :latest
  -> chatgpt.com/backend-api/codex                   the one enabled codex account
```

`<tailscale-addr>` is this host's Tailscale address. It is not committed: `deploy/.env` (untracked) holds
`TAILSCALE_ADDR=<the address>`, which `deploy/docker-compose.8318.yml` and `deploy/container-up.sh` read.

Neither port is published beyond loopback and the Tailscale address. An earlier pair (relay `:8371`, cliproxy `:8317`) belongs to
another checkout and is not maintained from here.

## Keeping it running

The relay is supervised by Docker; the cliproxy container is started by the harness's crontab (an `@reboot` line and the `:8318`
step of its nightly update). This repository's `WORKSPACE_PROTOCOL.md` names no other crontab entry for this pair.

- **A relay that crashes is started again by Docker** (seen once, on this machine: the container's init process killed with
  `kill -9` answered again after 1.1 s, the run log's chain intact). **A manual stop is not restarted**: Docker documents it for
  `docker stop` (a stopped container stays stopped across a reboot until `docker start`); `docker kill -s KILL` was tried, without a
  reboot, and left it down until started by hand.
- **At boot** the relay container may start before `tailscale0` has its address; the relay requires every address it listens on
  and exits, and Docker starts it again until the bind works (`docker.md`, "At boot"). A reboot has not been tried.
- **Back to the native relay** (the rollback; it reads the same config and run log, and cannot run together with the container:
  the run log is single-writer): `docker stop relay-8381 && docker rm relay-8381`, then

  ```
  env -i HOME="$HOME" PATH=/usr/bin:/bin RELAY_LOG_DIR="$HOME/.local/state/cliproxy-8381" RELAY_LOCK=/tmp/clisaving-relay-up.lock "$HOME/Sites/TOOL/lokki/core/relay-up.sh"
  ```

  `relay-up.sh` starts the relay only when nothing is bound on the configured addresses, and says so on stderr when something is
  bound and not answering. `RELAY_LOG_DIR` and `RELAY_LOCK` keep its log (`relay.log` in that directory) and its lock apart from
  the earlier pair's (`~/HARNESS/logs`, `/tmp/cliproxy-relay-up.lock`). `env -i` gives it a clean environment, because a `RELAY_*` variable in your shell overrides
  `config.yaml`. `/healthz` does not look at cliproxy. A native relay that exits stays down.

  The config symlink the native relay reads is `core/config.yaml` (git-ignored; it was `midstream-abort/config.yaml` before the directory moved, and git does not move an untracked link: recreate it with `ln -s ~/.local/state/cliproxy-8381-conf/config.yaml core/config.yaml`).
- **The cliproxy container has restart policy `no`** (below). After a reboot it comes up because the harness's `@reboot` line runs
  `deploy/container-up.sh`. After a Docker restart, a crash or a stop on purpose it stays down until someone runs that script from
  the main checkout, the machine reboots, or the harness's nightly step starts it. That step (`bin/cliproxy-update.sh` in the
  harness repository, which is the record of its side) pulls the image and runs `docker compose up -d` only while the Tailscale
  address is on an interface and the starter's lock is free, also after a failed pull (then on the image already on the host; read in
  the harness's code, not run here), then `deploy/container-up.sh --check`, and runs
  the starter once if the container is not up. It acts only on a container made by `docker compose -f deploy/docker-compose.8318.yml`
  in the main checkout (the compose project `clisaving-8318` and a `working_dir` label that is that checkout's `deploy/`). `up -d`
  recreates the container only if the image or the compose file differs from what runs, and starts a stopped one (documented for
  compose, not seen here). A Docker restart takes the container down too (`live-restore` is off), for instance the one the
  nightly system update triggers (the harness reports that one; the cliproxy's own stop was not seen here). The harness's step and the script share the lock
  `/tmp/clisaving-container-up.lock`: do not rename or move it without telling the harness. Do not put
  `relay-up.sh` in cron: Docker supervises the relay, and that entry would start a native relay beside a container that was
  stopped on purpose.
- **A checkout needs `deploy/.env`** before the boot line or the nightly step can start the container: without it (and with no
  `TAILSCALE_ADDR` in the environment, which a cron or `@reboot` run does not have) `container-up.sh` exits 64 and the compose file
  refuses to render.
- **Nothing alerts.** A dead relay or cliproxy is found when a client fails. A container whose `/healthz` probe fails is marked
  `unhealthy` and nothing acts on that.

### Why the container's restart policy is `no`

`cli-proxy-api-8318` publishes `<tailscale-addr>:8318`, and at boot Docker starts a container with `restart: unless-stopped` before
`tailscale0` has that address. The bind fails, and the container is then poisoned: it stays `Created`, and every later
`docker start` succeeds but leaves it running with no published port, which a stop and start does not undo. The relay's `/healthz`
would say healthy over a dead cliproxy. So the policy is `no`: Docker never makes that first, failing start, and a missing cliproxy
fails loudly (connection refused). The cost is the other half: a container that exits at any other time stays down, where
`unless-stopped` would bring it back in seconds. That the policy would poison the container at boot is inferred: the poisoning after
a failed first start was reproduced, a reboot was not tried.

### The scripts that are there for it

- **`deploy/container-up.sh`** starts the container, only when the address is up on an interface (it waits up to five minutes), and
  checks that its port is published (it stops a container that runs without it). `--check` only says whether it is up with its port
  published and changes nothing; any other argument is refused with exit 64. Exit 0 is "up and published", 1 "not up (`--check`),
  docker not answering, the container exited right after it started, or the address not up after five minutes", 2 "no such container",
  3 "needs recreating", 64 "a bad argument or no usable address". Docker erroring, or the port not showing for a moment, is read
  again (three reads, two seconds apart) and is not a verdict. Every docker call is cut off after 20 s, and a second run while another
  is waiting exits at once. A paused container counts as up.
- **Recreate, not restart, is the recovery** for a poisoned container: `docker rm -f cli-proxy-api-8318` and
  `docker compose -f deploy/docker-compose.8318.yml up -d` from the main checkout. After a failed start the script stops the
  container and leaves the marker `~/.local/state/cliproxy-8381/container-needs-recreate`; until the container is recreated every run
  says so and touches nothing, and the marker goes by itself when a plain run next sees the container running with its port published.
- **The boot line** is one `@reboot sleep 30` line in the harness's crontab block:
  `@reboot sleep 30 && "$HOME/Sites/TOOL/lokki/deploy/container-up.sh" >> "$HOME/HARNESS/logs/<host>/cliproxy.log" 2>&1`
  (`crontab -l` shows it). Nothing runs the script every five minutes; adding that is the Human's decision. Under policy `no` it
  would leave a container that exits (a crash, a Docker restart) down for up to five minutes, where Docker's own restart takes
  seconds, and it would start a container stopped on purpose again within five minutes.
- **`deploy/docker-compose.8318.yml`** is the container's definition (image `eceasy/cli-proxy-api:latest`, which the harness's nightly
  step follows; the pinned local build `cli-proxy-api-8318:20261004`, CLIProxyAPI v8.0.15, stays on the host for a way back: a copy
  of the compose file beside the original in `deploy/`, with that image, `docker compose -f <the copy> up -d`, the copy removed
  afterwards). The nightly step pulls from the original file, not from the copy, so when `:latest` has changed it recreates the
  container on it and undoes the rollback; a rollback that is to last needs the step paused or the file changed. The top-level `docker-compose.yml` is the earlier pair's definition: do not `up` it from here while the earlier pair
  runs.

## Operating

From the next image build, an operator token can call `GET /api/status`,
`GET /api/settings`, `POST /api/reload` and `POST /api/shutdown` on the relay.
The mounted settings file is read-only in this deployment, so `PUT
/api/settings` answers 409. See the [core API reference](../app/api.md) for
request and response details.

- **Which process is the relay.** `docker ps -a --filter name=relay-8381` (and `ss -ltnp 'sport = :8381'`). If the native relay is
  running instead (after the rollback), `pgrep -f lokki/core/server.py`; not `pgrep -f 'server.py --config'`, which
  also matches the earlier pair's relay.
- **Is it up?** `docker ps -a --filter name=relay-8381` (health), `docker logs --tail 20 relay-8381`, or
  `curl http://127.0.0.1:8381/healthz`. `/version` (a bearer token) shows the revision, the configuration fingerprint and the client
  names. `core/relay-up.sh --check` is the native relay's check. `deploy/container-up.sh --check` says whether the cliproxy
  container is up with its port published, and changes nothing.
- **A setting.** Edit `~/.local/state/cliproxy-8381-conf/config.yaml` (the real file; a plain `sed -i` on `core/config.yaml`
  replaces the symlink, see `docker.md`), then `docker kill -s HUP relay-8381` (for the native relay, `kill -HUP <relay pid>`):
  `seg_budget`, `total_cap`, `max_segments`, `tail_chars`, `merge_text`, `session_pin`, `text_calls`, `text_calls_pad`, `payload_cap`, `imagegen_cut`,
  `pacing_seconds`, `max_concurrent_upstream` and the client tokens are re-read for the runs that start after it, and a file that does
  not parse is refused. The listen addresses, the run log and the code need a restart.
- **New code.** `git pull --ff-only origin main` in the main checkout, `deploy/relay/build.sh --test <commit>`, then
  `RELAY_SHA=<commit> docker compose -f deploy/docker-compose.relay-8381.yml up -d` (`docker.md`, "Upgrade"): the old container drains
  for up to 30 s and the new one starts; until then the port refuses connections. Check `/version` for the commit afterwards.
- **The checkout** does not decide what runs: the container holds the code of the commit it was built from, so a dirty tree or another
  branch in the main checkout changes nothing until the next build (which builds a commit, not the tree). It still matters for the
  native fallback, which runs whatever is on disk in the main checkout when it starts. Development happens in worktrees under
  `.claude/worktrees/`, never in that checkout.
- **Rollback.** To the previous image: the same `up -d` with the previous `RELAY_SHA` (keep the old images). To the native relay:
  "Keeping it running" above. To older native code, `git switch --detach <previous sha>` in the checkout first: a revision from before
  a setting existed ignores the keys it does not know, so check `/version` for what it ran with; `git switch main` and
  `git pull --ff-only` to return.
- **Usage.** The `usage-report` plugin in cliproxy (`/v0/management/plugins/usage-report/api/usage`, management secret in
  `~/.config/cliproxy/mgmt_secret`) records the requests the provider finalizes; the relay cuts most of its own, so it undercounts
  relayed traffic ([`usage-oracle.md`](usage-oracle.md)). The 5h meter (`used_percent`) is an integer.
- **Accounts.** One codex account is enabled.

## Pointing a client at it

Codex takes its providers from `~/.codex/config.toml`, or from `-c` on the command line: it ignores `model_provider` and
`model_providers` in a project's `.codex/config.toml`, so the entries cannot live in a project folder. Add these two to
`~/.codex/config.toml` and select the pair with `model_provider = "relay_live"` or `codex -c model_provider=relay_live`. The key names
are environment variables, never the values (`RELAY_API_KEY` is the relay's client token, `CLI_PROXY_API_KEY` cliproxy's):

```toml
[model_providers.relay_live]
name = "relay :8381"
base_url = "http://127.0.0.1:8381/v1"        # or http://<tailscale-addr>:8381/v1 from another tailnet host
env_key = "RELAY_API_KEY"
wire_api = "responses"
supports_standalone_web_search = true

[model_providers.cliproxy_live]
name = "cliproxy :8318"
base_url = "http://<tailscale-addr>:8318/v1"
env_key = "CLI_PROXY_API_KEY"
wire_api = "responses"
supports_standalone_web_search = true
```

Making `relay_live` the default provider sends everyday Codex traffic to one account: that is the Human's decision. The `cliproxy`
provider that may already be in `~/.codex/config.toml` is the earlier pair's cliproxy and does not pass through this relay;
`relay_live` is the one that does.

## What this pair is, and is not

- **Meter readings on the live pair include every client's traffic in that window.** Take readings with `core/billing_probe.py`
  when nobody else is using the pair. The harness that ran measurement rounds here, `core/ab_codex.py`, was removed in
  `21f14bc9d33c4966831f6fdac6348ac831008518`.
- **The relay is not a free saving.** What was measured, each with its limits, is in [`cost-of-a-cut.md`](cost-of-a-cut.md) and in
  `relay-8371.md`, "When to point a client at the relay".
