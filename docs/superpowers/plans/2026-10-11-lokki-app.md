# lokki App Implementation Plan

> **For agentic workers:** execute this plan task by task, in order, with the `superpowers:executing-plans` skill when the seat has the superpowers plugin, otherwise as written. Steps use checkbox (`- [ ]`) syntax for tracking. Each task names its gate. The gates that exist today stay green throughout: `cd core && python ci_quiet_suite.py` (it fails on any byte a test writes, any file left in its TMPDIR, any failing test and on no test found), `cd ui && npm run check && npm test`, and from Task 1 `cd ui && npm run e2e`. A pull request that adds a test carries, in its body, one sentence per new test naming the behaviour that test binds and no existing test does; a behaviour an existing table can hold is a row there, not a new test function.

**Goal:** A desktop application for Linux, macOS and Windows that installs, starts and supervises the core and CLIProxyAPI, shows the core's UI in its window, lets the user add a Codex account from that UI, and has no business logic of its own.

**Decided by the pinned binary, not by the plan:** CLIProxyAPI 8.0.23's management API has one Codex login flow, the browser one; `codex-auth-url` answers `{state, status, url}` with and without `is_webui=true`, and no route gives a device code (every spelling of one is a 404; the "device code" strings in the binary belong to its own CLI). The device-code flow the owner asked for therefore has no backend in this release and is not in this plan; it returns when a pinned release serves one. With `is_webui=true` CLIProxyAPI also opens its callback forwarder on `0.0.0.0:1455`, every interface, with no key to bind it narrower, so the plan does not use `is_webui`: the core owns the callback listener, on loopback (decision 9).

**Architecture:** `app/` is a Tauri v2 shell in Rust with no frontend of its own: its window loads the core's `/` over loopback (spec 6.4), so the UI and the API are one origin. The shell (1) finds the data directory and runs `lokki-core init` there, then reads what it needs from `lokki-core shell-config` on a pipe (spec 3.8), so it parses no YAML; (2) runs `lokki-core sync-cliproxy` before each CLIProxyAPI start, so CLIProxyAPI's file carries the port, the loopback host and the panel switch the core's settings hold; (3) spawns the two sidecars with `std::process::Command` in their own process group (on Windows, the tree is what `taskkill /T` takes), CLIProxyAPI then the core, and supervises them with a bounded restart (spec 6.1); (4) injects into the window a script that adds the operator header to requests to the core's origin and defines `window.lokki` with four hooks: `restart(service)`, `openExternal(url)`, `openPanel()`, `copyManagementSecret()` (spec 6.4, `docs/app/ui.md`); (5) has a tray with open, pause/resume and quit; (6) shows one bundled error page when `init` fails or a sidecar gives up; (7) stops the core through `POST /api/shutdown` first. Adding a Codex account is the core's work (spec 4.7: two routes that drive CLIProxyAPI's OAuth and a loopback listener for the provider's callback) and the UI's (the CLIProxyAPI tab); the shell only opens the provider's URL in the system browser. CLIProxyAPI's own panel is off by default (`cliproxy.panel`), and when on it opens in the system browser, never in a shell window. Sidecars are `bundle.externalBin` files named with the product version; `lokki-core` is PyInstaller's one-file build of the core with the built UI inside; `cliproxy` is the official release binary for the OS and arch, verified against the hashes pinned in `app/cliproxy.lock`. The updater (spec 7) is sub-project 5: this plan leaves `plugins.updater` unset.

**Tech Stack:** Rust stable (rustup, minimal profile; the workstation has 1.99 in `~/.cargo`, not on PATH); `tauri` 2.12 with the `tray-icon` feature, `tauri-build` 2.7, `tauri-plugin-opener` 2 and `tauri-plugin-clipboard-manager` 2 (both used from Rust only; no JS permission), `libc` 0.2 (the POSIX signal to a process group), `serde`, `serde_json`, `reqwest` 0.12 blocking with `default-features = false` (loopback HTTP only, no TLS) for `/healthz`, `/api/shutdown`, `/api/status` and the pause setting; `@tauri-apps/cli` 2.12 via npm for `tauri build`; Node 24 (`node --test` for the injected script); Python 3.13 with `pyyaml` 6 and PyInstaller 6.22 (`~/.local/bin/pyinstaller` is 6.22.3) for the core sidecar; `xvfb`, `dbus` for the headless smoke on Linux. Every version pinned exactly where a lock file exists (`Cargo.lock`, `app/package-lock.json`) and with `==` where pip installs. The crate versions at the time of writing: `tauri` 2.12.3, `tauri-build` 2.7.2, `tauri-plugin-opener` 2.7.1, `tauri-plugin-clipboard-manager` 2.4.2, `libc` 0.2.190; the Lead re-reads them at Task 2 with the major given (`cargo info tauri@2`, `libc@0.2`: a bare `cargo info` names the 3.0 alpha).

**Spec:** `docs/superpowers/specs/2026-10-10-lokki-app-design.md` sections 6 (6.1 to 6.4), 3.8 (`init`, `sync-cliproxy`, `shell-config`), 4.7 (adding an account), 2 (the secrets), 8 (layout), 9 (security); `docs/app/ui.md` (the contract the UI expects), `docs/app/data-directory.md`, `docs/app/api.md`. Facts the plan rests on, checked on 2026-10-11 against the pinned release and on 2026-10-13 against its Linux binary: CLIProxyAPI 8.0.23's archives are `CLIProxyAPI_8.0.23_<os>_<arch>.tar.gz` (darwin and linux, `amd64`/`aarch64`) and `.zip` (windows), each holding the binary `cli-proxy-api` (`.exe` on Windows) beside `README.md`, `README_CN.md`, `LICENSE` and `config.example.yaml`; the release also carries `_no-plugin` variants, which the lock does not name; `checksums.txt` lists `<sha256>  <asset>` lines; `server.host` empty means "bind all interfaces" and `127.0.0.1` restricts it; `management.disable-control-panel: true` turns off both the panel's download from GitHub and its route; the panel otherwise is `/management.html`; `/v0/management/*` and `/v8/management/*` take `Authorization: Bearer <secret>` (what the core's reader uses); `GET /v0/management/codex-auth-url` answers 200 `{state, status, url}` where `url`'s `redirect_uri` is `http://localhost:1455/auth/callback`, and `GET /v0/management/get-auth-status?state=` answers `{status: "wait" | "ok" | "error", error}` (an unknown or expired state is `error`, a malformed one 400, an empty one `ok`); `POST /v0/management/oauth-callback` takes JSON `{code, state, error}` with no management key (`internal/api/handlers/management/oauth_callback.go` at the tag: it writes the session's `.oauth-codex-<state>.oauth` file, which the login goroutine picks up and exchanges with the provider; an unknown state is 404, a repeat 409, and CLIProxyAPI waits five minutes for it); `cli-proxy-api -h` prints `CLIProxyAPI Version: 8.0.23, …` as its first line and exits 0 (`--version` exits 2); at start the binary fetches two version strings from npm, its own traffic; about ten failed management logins from one address earn a 403 `IP banned … 30m` that refuses the right secret too; `init` prints one JSON line `{created, core_port, cliproxy_port, core_config, cliproxy_config}` and no secret; the operator token is the `auth.tokens` entry named `app`; the management secret is `secrets/cliproxy-mgmt.secret`; `POST /api/shutdown` answers 202 `{stopping, drain_seconds}`; `PUT /api/settings {"routing": …}` is the pause.

Installers for Linux arm64 and Windows arm64 (spec 6.4) wait for a runner that builds them; the plan declares that, it does not build them.

**Decisions the plan takes (where the spec was open, or where the plan departs from it and the spec is amended in the same change):**

1. **Sidecar names.** Tauri resolves an `externalBin` entry by its name plus the target triple, and its Windows path helper treats a dot in the name as an extension, so the version goes in with dots replaced by underscores: `lokki-core-0_1_0`, `cliproxy-8_0_23`. `app/scripts/sidecars.py` is the one home of that rule: `fetch_cliproxy.py` and `build_core.py` import it, `build.rs` runs `python3 scripts/sidecars.py --names` and bakes the two names into constants, and `tauri build` receives `bundle.externalBin` and `version` as a `--config` override printed by `sidecars.py --config-json`. The tracked `tauri.conf.json` names no `externalBin`, so `cargo test` and `cargo check` never need the sidecar files. At start the shell deletes files in its own directory whose name starts with `lokki-core-` or `cliproxy-` and does not carry the current version; errors are ignored (the directory is read-only in a `.deb`, a `.app` and an AppImage; the case this covers is NSIS, whose directory is the user's).
2. **The panel.** The panel is third-party JavaScript downloaded from GitHub at run time. In a Tauri window it would sit beside `window.__TAURI__` and need a capability of its own; in the system browser it gets nothing from the shell. So `openPanel()` opens `http://127.0.0.1:<port>/management.html` with the OS's browser, and `copyManagementSecret()` puts the secret on the clipboard for the panel's login form, on the user's click. The secret reaches no page and no URL. The panel exists only when `cliproxy.panel` is on, which is off by default.
3. **Pause** in the tray is `PUT /api/settings {"routing": "direct"}`; **Resume** writes back the value `routing` had before the pause (`auto` when the shell did not pause it). The label follows `/api/status.routing`, read every 30 s and after each toggle (the tray API has no "menu opened" event on Linux).
4. **Logs.** Sidecar stdout and stderr go to `DIR/logs/core.log` and `DIR/logs/cliproxy.log`, rotated by the shell at 5 MB (one `.1` kept). The shell's own log is `DIR/logs/app.log`. No line of any log carries a token or the secret: the shell never prints them and never logs a sidecar command's stdout (`shell-config` prints the token there), and the sidecars do not either.
5. **The error page** is one bundled HTML file (`frontendDist`, the app's own origin), opened when `init` or `shell-config` fails (no window exists yet) and when a sidecar gives up (the last 50 lines of its log, "Try again"); nothing restarts on its own after a give-up.
6. **A CLIProxyAPI restart restarts the core too**, in the spec's order (core drained and stopped, CLIProxyAPI stopped, `sync-cliproxy`, CLIProxyAPI started, core started): the core reads its upstream address at start and a reload holds it, so a port change needs both.
7. **No `tauri-plugin-shell`.** Sidecars are spawned with `std::process::Command` from the directory of the running executable (where Tauri's bundler puts `externalBin` files), in a new process group on POSIX and with `CREATE_NO_WINDOW` on Windows; the fallback kill takes the group (`libc::kill(-pgid, …)`) and, on Windows, the tree (`taskkill /T /F /PID`), because a PyInstaller one-file build is a bootloader whose Python child keeps the port when only the parent dies. The page gets no shell permission. The three core subcommands the shell runs (`init`, `shell-config`, `sync-cliproxy`) get the same scrubbed environment as the sidecars, their stdout captured on a pipe and never inherited.
8. **The window's IPC grant** is one runtime capability for the label `main` and the core's exact origin (`CapabilityBuilder` with `remote`, added once the port is known), listing the four app commands the page uses and nothing else, plus `smoke_done` only when `LOKKI_SMOKE` is set; the error window gets its own local capability (`window("error")`, no `remote`) with `try_again`. `build.rs` declares those commands in the app manifest so they are gated by those capabilities. The main window may navigate only within the core's origin; any other URL is refused, and the UI opens external links through `openExternal`, which accepts `https:` only.
9. **The OAuth callback is the core's.** The login URL CLIProxyAPI builds sends the browser back to `http://localhost:1455/auth/callback`. The core listens there, on `127.0.0.1` only, while one flow is pending (five minutes, CLIProxyAPI's own wait for the callback; one flow at a time; a busy port is a 409 "another login is in progress", since `codex login` uses the same port), hands what the provider sent, `code` or `error` with `state`, to CLIProxyAPI through `POST /v0/management/oauth-callback` (JSON `{code, state, error}`; the route takes no management key, and its 200 means accepted, not logged in: the login finishes in CLIProxyAPI and shows in `get-auth-status`), and answers the browser from that answer: "you can close this tab" on a 200, "this login expired, start again" on a 409. The browser must therefore run on the machine the app runs on; `docs/app/limits.md` says so.

## Global Constraints

- The shell holds no business logic: it never reads or writes a settings key except `routing` for pause/resume, never edits CLIProxyAPI's file except through `lokki-core sync-cliproxy`, never reads `cliproxy/auth/`, and never adopts a CLIProxyAPI already running on the machine (spec 6.3).
- Both sidecars listen on loopback only: the core by its `listen`, CLIProxyAPI by `server.host: 127.0.0.1`, both written by `init` and kept by `sync-cliproxy`; the core's callback listener binds `127.0.0.1:1455`; the shell passes nothing that could change any of that. The sidecars' environment is an allow-list (decision 7, Task 3): CLIProxyAPI reads `MANAGEMENT_PASSWORD`, the credential-store variables and more, and the core reads `RELAY_*`, `CLIPROXY_*` and `CLI_PROXY_API_KEY`; none of them reaches a sidecar from the user's shell.
- The operator token and the management secret are read into memory from `shell-config`'s pipe and the secret file, and never written to a log, a URL, the clipboard without the user's click, or a window title; the token is interpolated into the injected script's closure only.
- Every test runs without a display except the smoke, which runs under `xvfb-run`; no test reaches the network. The sidecar fetch (a build step, not a test) downloads from `github.com/router-for-me/CLIProxyAPI/releases` and verifies the hash from the lock before the archive is opened; the AppImage bundling step downloads its tools from GitHub too, and the plan says so where it runs.
- Nothing binds `:8381` or `:8318` on the workstation: the smoke and every developer run use `LOKKI_PORTS=0,0`, so `init` picks free ports.
- Shutdown order: `POST /api/shutdown` to the core, wait up to `drain_seconds + 5` s (the value from the 202 body), kill the group; then CLIProxyAPI (SIGTERM to the group, kill after 5 s; `taskkill /T /F` on Windows) (spec 6.1).
- Commands chained in a gate use `&&` only; no `| tail` hides a status.
- Commit messages end with the attribution lines the session carries; `git add` names paths.

## Review Focus

1. A core that exits four times within a minute is not restarted a fourth time; the error page shows its log tail (Task 3 `a_fourth_exit_in_a_minute_gives_up`).
2. Quit sends `POST /api/shutdown` with the operator token before any kill, and kills only after `drain_seconds + 5` s from the 202 body (Task 3 `the_core_is_drained_before_it_is_killed`).
3. The injected `fetch` adds `X-Relay-Token` only to requests whose URL is the core's origin, does nothing on any other origin, and does not expose the token through `fetch.toString()` (Task 4 `inject.test.mjs`); from the real page, `fetch("/api/status")` is authenticated and `window.lokki.restart("cliproxy")` resolves (Task 4 smoke, `smoke: page status=200 restart=ok`).
4. A sidecar file of another version is deleted at start and the current ones are kept (Task 3 `old_sidecar_files_are_removed`).
5. The fetched CLIProxyAPI archive is refused when its hash differs from the lock's, before it is opened (Task 2 `test_a_wrong_hash_is_refused_before_extraction`).
6. CLIProxyAPI listens on `127.0.0.1` only (Task 0a `the_cliproxy_file_binds_loopback_and_hides_the_panel`; Task 4 smoke, the listener line).
7. None of the four generated secrets appears in `app.log`, `core.log`, `cliproxy.log` or the app's stdout (Task 4 smoke).
8. `POST /api/accounts/oauth` never reads `cliproxy/auth/` and never answers a credential; the callback listener binds `127.0.0.1` only and hands `code` and `state` to CLIProxyAPI once (Task 0b `oauth_start_returns_what_cliproxy_gave_and_opens_the_loopback_listener`, `the_callback_is_handed_to_cliproxy_once_and_the_listener_closes`).

### Task 0b: The core adds a Codex account, and the reader's two guards

**Files:**
- Create: `core/lokki_core/quota/oauth.py`
- Modify: `core/lokki_core/quota/reader.py` (an opener with no proxy), `core/lokki_core/quota/poller.py` (the hold after a refused secret), `core/lokki_core/handler.py` and `core/lokki_core/control.py` (the two routes), `core/test_quota_reader.py` (the fake gains the three OAuth routes; rows), `core/test_quota_poller.py` (rows), `core/test_control.py` (`AccountsRouteTests` rows; the route lists the `RouteMatrixTests` iterate), `docs/app/api.md` (the two routes and their statuses), `docs/app/limits.md` (the OAuth routes are CLIProxyAPI's legacy management API; the provider sends the browser back to `localhost:1455`, so the browser runs on the app's machine, the port is shared with `codex login`, and a server or Docker core cannot take the callback from a remote browser; the provider's login page is the provider's; CLIProxyAPI fetches two version strings from npm at start, its own traffic)

**Interfaces:**
- `oauth.start(management_url, secret, timeout=10.0) -> {state, url}`: `GET <management_url>/v0/management/codex-auth-url` (no `is_webui`: that would make CLIProxyAPI bind `0.0.0.0:1455`) with `Authorization: Bearer <secret>`, the header the reader uses and the binary honours. A non-200, non-JSON or missing field is a `ManagementError`.
- `oauth.status(management_url, secret, state, timeout=10.0) -> ("pending" | "ok" | "error", error_text)`: `GET /v0/management/get-auth-status?state=<state>`; the binary's `wait` is `pending` here, its `error` carries its text.
- `oauth.Callback(port=1455)`: a listener on `127.0.0.1:<port>` for one pending flow (the tests inject a free port, so the suite never binds 1455), started by `start` and closed on `ok`, on `error`, after five minutes (CLIProxyAPI's own wait: a later code earns a 409 from it), or when the next `start` replaces it; `GET /auth/callback` with `state` and `code` or `error` hands them to CLIProxyAPI once through `POST /v0/management/oauth-callback` as JSON `{code, state, error}` with no management key (the route takes none), and answers the browser from CLIProxyAPI's answer: a plain "you can close this tab" page on a 200, "this login expired, start again" on a 409; any other path, a request without `state`, or one with neither `code` nor `error`, is a 404 with nothing handed on; a second callback for the same state is handed on and answers what CLIProxyAPI says (its 409). The listener's `log_message` is silenced: the default writes the query, `code` included, to stderr. A port already bound (another login, `codex login` itself) makes `start` raise `CallbackPortBusy`.
- `POST /api/accounts/oauth`, operator, an empty or `{}` body: the management secret file is read first (409 `{error}` when unreadable, before anything binds), then the listener binds (409 on `CallbackPortBusy`), then CLIProxyAPI is asked (502 `{error}` on a `ManagementError`, and the listener closes); 200 `{state, url}`. `GET /api/accounts/oauth/<state>`, operator: `state` must match `[A-Za-z0-9_-]{8,128}` (else 400; the binary answers `ok` to an empty state, so this guard is not decoration); 200 `{status, error}`; 502 on a `ManagementError`, a 401 or a 403 from CLIProxyAPI included. On `"ok"` the handler closes the listener and calls `poller.POLLER.wake()`. The core keeps no OAuth state but the listener and never opens a browser. Both routes are under the Host/Origin guard and the operator gate: the `<state>` route is a prefix match, so `do_GET` checks `client_operator` for it explicitly, as the POST tuple does (`handler.py`'s operator tuples are exact matches).
- `reader._request` uses `urllib.request.build_opener(urllib.request.ProxyHandler({}))`: the management API is the core's own loopback neighbour (or the operator's `cliproxy.url`), and a system proxy must not see those calls. `oauth` uses the same function.
- `reader.ManagementError` gains `status` (the HTTP status that caused it, else `None`), set where it is raised; `poller`: after a read whose `ManagementError.status` is 401 or 403, the loop sleeps until `wake()` (a reload or a refresh) instead of `poll_seconds`; `last_error` reads `"<the error>; polling paused until a reload or a refresh"`.
