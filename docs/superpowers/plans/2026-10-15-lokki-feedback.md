# lokki Feedback Implementation Plan

> **For agentic workers:** execute this plan task by task, in order, with the `superpowers:executing-plans` skill when the seat has the superpowers plugin, otherwise as written. Steps use checkbox (`- [ ]`) syntax for tracking. Each task is one pull request, branched off `lokki-feedback` after the previous task's PR has merged; one PR at a time. Each task names its `Owner` (who implements its PR and who reads it), its `Invariants` (what its PR must leave true, beside the Global Constraints), its `Depends on`, its `Reopen when` (the premise whose failure sends the task back to the plan instead of being worked around), and its gate. No task's PR is red, and no merged task leaves a state a user would see half-built (decision 1). A PR body carries one sentence per new test naming the behaviour that test binds and no existing test does (a behaviour an existing table can hold is a row there, not a new test), the test counts before and after that its gates printed, and, for a UI change, the screenshot table of decision 16.

**The gates.** Each task's gate step names which of these it runs; G-core, G-ui, G-scripts and G-inject run in every task.
- **G-core** `cd core && python ci_quiet_suite.py`
- **G-ui** `cd ui && npm ci && npm run check && npm test && npm run e2e`
- **G-scripts** `cd app/scripts && python3 -m unittest`
- **G-inject** `cd app && node --test 'inject/*.test.mjs'`
- **G-rust** `cd app/src-tauri && ~/.cargo/bin/cargo fmt --check && ~/.cargo/bin/cargo clippy --locked --workspace -- -D warnings && ~/.cargo/bin/cargo test --locked --workspace`, only in a task that changes something under `app/` (Tasks 3 and 9)
- **G-smoke** `cd app && bash smoke/smoke.sh`, in Tasks 3 and 9 (the shell's binary changes)
- **CI:** `core.yml`, `ui.yml` and `app.yml` green on the PR's head (each runs on its own `paths`; `ui.yml` runs for any change under `core/lokki_core/`, so the e2e sees every core change).

**Host rules** (every task, every command): ports 0 (`LOKKI_PORTS=0,0`; the e2e's `init --core-port 0 --cliproxy-port 0`), never `:8381`, `:8318` or `:1455`; a test of the callback listener binds an injected ephemeral port (`oauth.CALLBACK_PORT` patched), as the existing listener tests do. The lokki app in the desktop session, with its data under `~/lokki-test/`, and its processes are left alone. For any Rust build (G-rust, G-smoke): `CARGO_BUILD_JOBS=4`, one scratch `CARGO_TARGET_DIR` outside the checkout deleted after the gate, 10 GB free on `/`, no build while a runner job is queued or running, `~/.cargo/bin/cargo` (it may not be on a non-interactive `PATH`), and CI's pinned virtualenv for PyInstaller. Every other scratch outside the checkout, removed after; stop what you start by pid; `node_modules`, the UI build output and `__pycache__` removed before the PR is handed back.

**Goal:** The six points of the feedback spec. Low Quota Mode goes: Relay always cuts, Direct always passes through, Auto is the low-quota rule, with the quota read in every mode and every existing settings file keeping what it did; Auto can name the models it cuts; a Codex login finishes from a browser on another machine by pasting the address it ended on; `text_calls` is on by default; Settings shows what a user of the app changes and folds the rest under Advanced; and on macOS the app installs its own updates where it can replace its bundle.

**Architecture:** Nine PRs. Task 1 flips one schema default. Task 2 makes the reader and the policy give every account its own state, watched or not, and puts a guard round the quota rule; the one change a user sees is that, with named accounts, an account outside them shows its own figure and reset under "not watched" where it showed "no reading". Task 3 is the contract change of point 5 in one PR across the core, the UI and the tray (decision 1): `low_quota.enabled` is retired by `migrate.RETIRED` at every load and write, `routing` defaults to `relay`, `decide` takes the poller's read error and answers the new reasons, the poller reads in every mode, and the UI and the tray stop reading and writing the retired key. Tasks 4 and 6 draw the new modes in Settings, Home and Accounts, and Task 6 makes the threshold the one control a user moves: the mode slider on Home and in Settings › Mode (decision 21); Task 5 adds `low_quota.models`, `policy.for_model`, `GET /api/models` and the Settings picker together, because the row cannot ship without its control (decision 2). Task 7 gives the core one `hand_on` for the listener and the new paste route `POST /api/accounts/oauth/<state>`, and Task 8 the paste field. Task 9 replaces `macInstall` with a policy read from the running bundle and computed again before the download and before `install`; it merges only after the signer's hand test on an Intel Mac, and refuses the install in place on Apple silicon until a later PR lifts that refusal (decision 20). No page command, no dependency, no new store.

**Tech Stack:** what the tree already pins. Python 3.13 standard library and `unittest` for the core and the app scripts; Svelte 5.57, TypeScript 6.0, Vite 8.3, Vitest 5.0, `@testing-library/svelte` with jsdom, `@playwright/test` 1.64 (Chromium) for the UI; Rust with `tauri` 2.12.3, `tauri-plugin-updater` =2.13.3 and `libc` =0.2.190 (unix) for the shell; `@tauri-apps/cli` 2.12.2 for the builds. No dependency is added.

**Spec:** `docs/superpowers/specs/2026-10-15-lokki-feedback-design.md`, the whole of it, with its prototypes `docs/design/ux/home.html`, `accounts.html`, `settings.html` and `tray.html`. **Decisions the plan takes:**

1. **The retirement of `low_quota.enabled` is one PR across the core, the UI and the tray (Task 3).** The proposed split put the core's file side, the core's decision, the UI's modes and the tray's Auto in four PRs. None of them can merge alone without a state a user sees broken: with the key retired at load but the old `decide`, an app whose user turned Low Quota Mode on cuts every request and its switch reads off; with the new `decide` but the old default and no `migrate`, a server file without `routing` passes every request through at full price; with the core's allow-list losing the key, the UI's Auto, its switches and the tray's Auto answer 400, and the top bar says "Low Quota Mode is off, so Auto cuts every request" because `/api/status.low_quota` no longer carries `enabled`. The gates say the same: `ui.yml` runs the e2e for any change under `core/lokki_core/`, and the e2e writes and reads the key. So Task 3 carries the core change, the UI's removal of every read and write of the key, `modeBody` and the tray's `Mode::body`; what it leaves for Tasks 4 to 6 is drawing, not correctness: after Task 3 every control writes what the core accepts and every sentence is true (Home and Accounts show their cards and chips in every mode, as they did with Low Quota Mode on; the quota-read banner shows on any read error while a secret file is set, and without one Home says lokki does not read the quota here). What is not part of the contract change leaves Task 3: Task 2 (every account's own state and the guard, invisible with the old reasons) lands before it, and the models (Task 5) after.
2. **`low_quota.models`, `for_model` and `/api/models` land with their Settings picker (Task 5),** after the Settings layout (Task 4). A list row in the `saving` group with no control of its own would render as a text field Settings cannot save. Home's rule line (Task 6) then reads `models` from the start.
3. **Relay and Direct never call `decide`; the accounts still get their states.** The spec's table lists `routing: relay` and `routing: direct` as `decide`'s first rows, and says Relay and Direct never reach `decide`. `decide` keeps those rows (it is the pure function the table tests), and `routing.decide_now` reads `config.ROUTING` first: for `relay` and `direct` it answers without calling `decide`, with `per_account=policy.states(...)` and `watched=policy.watched(...)`, so `/api/accounts` shows every account's own state in every mode. The two decisions have one home, `policy.fixed(routing, per_account, watched) -> Decision | None` (`Decision(True, "routing: relay", …)`, `Decision(False, "routing: direct", …)`, `None` for `auto`): `decide`'s first rows and `decide_now` both answer through it, so the rows the table tests are the ones production answers. The guard (decision 4) covers both calls: a raise while stating the accounts under Relay leaves the decision `routing: relay` with no states.
4. **The guard** catches any exception from the quota code inside `decide_now` and answers `Decision(False, "the quota rule failed")` under Auto. It prints `[routing] the quota rule raised <ExceptionType>` (the type's `__name__`, never the message) when the raised type differs from the last raise (`None` after a call that did not raise), besides the usual change line. `policy.FAILED = "the quota rule failed"` is the string's home.
5. **The decision's reasons** are `policy.REASONS`, the one home, each string once, in the order of spec 3.4's table (which is not quite the order `decide` tests them: under `all`, `not every watched account is low` is tested before `a watched account could not be read`, as the rule below says): `routing: relay`, `routing: direct`, `the quota cannot be read`, `the quota is not read yet`, `no account to watch`, `no watched account could be read`, `every watched account is low`, `a watched account could not be read`, `not every watched account is low`, `a watched account is low`, `no watched account is low`, then `this model is not cut when low` (Task 5) and `the quota rule failed`. Under Auto: no snapshot and `read_error` set → cannot be read; no snapshot → not read yet; no watched account in the snapshot → no account to watch; every watched account `unknown` → no watched account could be read; under `all`, any watched account `ok` → not every…, else any `unknown` → could not be read, else cut with every…; under `any`, any `low` → cut with a watched account is low, else any `unknown` → could not be read, else no watched account is low. A snapshot is used whenever there is one; `read_error` decides only without one (staleness already ages a snapshot).
6. **`migrate` reads the retired value with `_flag`'s truth set,** not `_strict_flag`: the spec cites `_strict_flag` (`config.py:246`), which raises on a typo, and asks for a typo to read as not true and never refuse the file, which is `_flag`'s rule (`config.py:233`). `migrate` imports nothing from `config` (it is imported by it); the set `("1", "true", "yes", "on")` and `True` are its own, with a test row per word.
7. **`routing`'s choices are listed `relay`, `auto`, `direct` in `schema.py`,** as spec 3.2 lists them, with the default `relay`. What a user sees lists them `direct`, `auto`, `relay`, the slider's order from left to right (spec 3.1): `MODES` and the tray's `Mode::ALL`, both changed in Task 3.
8. **The login's hand-on has seven results.** The spec's `expired` names two causes the paste route answers differently; `oauth.hand_on(state, code, error)` answers one of `accepted`, `not waiting` (no login pending, or its 300 s passed), `another login` (the state is not the pending login's, a login whose state CLIProxyAPI has not named included), `already answered` (while CLIProxyAPI is asked, or after its 200), `expired` (CLIProxyAPI 404, for this answer or an earlier one), `refused` (CLIProxyAPI 409, likewise), `unreachable` (any other status, no answer, or a failed post; the login is marked unanswered again). The login keeps its result, so after `expired` or `refused` a second answer gets that result again (spec 4.2, step 3). The listener's page for `not waiting` and `expired` is the spec's `expired` row.
9. **One query rule for both entries.** `oauth.callback_query(query: str) -> tuple[str, str, str] | None` answers `(state, code, error)` when every name appears at most once, `state` is present and non-empty, and exactly one of `code` and `error` is present and non-empty; other names (the provider adds `scope`) are ignored and never handed on; anything else is `None`. It reads the query with `parse_qs(query, keep_blank_values=True)`, so a name given with a blank value counts as present: `state=a&state=` is a name given twice, `code=x&error=` gives both, and `state=` alone is a `state` that is empty; each is `None`, as spec 4.3 reads. The listener answers `None` with its 404 "Not found."; the route with its 400 for an address that is not the callback address. The address's port must equal `oauth.CALLBACK_PORT`, so a test that injects the listener's port pastes that port. The route reads the address through `oauth.pasted_callback(text: str) -> tuple[str, str, str] | None`, which never raises: it trims the text with `str.strip()` (the spec says spaces; this also takes the tab or trailing newline a copy can bring), splits it with `urlsplit`, and answers `None`, so the route's fixed 400, for a scheme other than `http`, a host other than the two, a port other than `CALLBACK_PORT`, a path other than `/auth/callback`, a user part, a `#fragment` (the callback address carries neither), a `callback_query` of `None`, and any `ValueError` that `urlsplit`, `.port` or `.hostname` raises. A raise there would reach `_internal_error`, which prints the exception's text, and that text can hold the pasted port.
10. **`GET /api/models` reads CLIProxyAPI through the reader's opener** (`reader._OPENER`, no system proxy), with the core's key in `Authorization: Bearer`, 10 s: the key is the core's credential, and the management calls already keep it off a proxy. Its 502 sentences are the spec's three, fixed.
11. **The update line has one home for its words.** `ui/src/lib/update.ts` `updateWords(u: UpdateStatus): {line, reason, error}` holds the sentences `Update.svelte` says today, and both the banner and Settings › Updates and About say them through it: `line` is `updateLine(u): string` (checking, downloading, installing, up to date, available, idle), `reason` the shell's reason where the banner shows it (beside an offer it cannot install, and beside "up to date"), `error` the shell's error, each said as it comes and each in its own element, since the error is styled apart; "Check now" in both is `checkNow`.
12. **`watchedCount` and `ruleLine` live in `mode.ts`,** the home of the modes' words. `watchedCount(accounts: Accounts | null): number | null` is the number of rows of the last accounts read that the core marks `in_scope`, `null` while none has answered (no read, `read_at` null, or not loaded): the core is the one home of who is watched, so a named account that is not among the rows is not counted, just as Accounts shows it as "Watched but not found". `ruleLine(lowQuota, watched: number | null, t = lowQuota.threshold_percent)`, `t` being the slider's position while it is held or stepped: `watched === 1` → "Cut when the watched account has less than <t> % left"; else `rule === "any"` → "Cut when any watched account has less than <t> % left"; else "Cut when every watched account has less than <t> % left"; then " · every model" for an empty `models`, else " · <n> model" / " · <n> models". The line says "Cut", not "Relay": a request Auto sends through the relay is one it cuts, and "Cut" is the word of Auto's sentence, the decision's headline ("Cutting every request") and the schema's labels ("Cut below, % left", "Cut when", "Models cut when low"), where "Relay" names a mode, which Auto is not.
13. **Accounts in Relay and Direct shows no `low` or `ok` chip,** as Home: the threshold decides nothing there; an account that could not be read keeps `unknown` with its error.
14. **The writability and read-only probes run on every unix.** `statvfs` with `ST_RDONLY` (the POSIX form of `statfs`'s `MNT_RDONLY`) and `access(W_OK)` are called through `libc` under `cfg(unix)`, so they compile, pass clippy and are tested on Linux; only the call that fills a `MacBundle` from `current_exe()` is macOS-only.
15. **The policy is a closure the machine calls.** `Machine::new(source, clock, current, policy: Box<dyn Fn() -> Policy + Send + Sync>)` computes it at start, again at the press before the download, and again after the stop before `install`; `status()` reports the last one computed. The refusals keep their order: an install running, then no update (the smoke's sentence), then the policy.

## Global Constraints

Copied from the brief and the spec; every task holds them.

- The UI works in a plain browser against a server or Docker core, with no shell hook.
- The seven `window.lokki` hooks equal `ui/src/lib/lokki.d.ts`; no new page command; `build.rs`, `capability.rs`, `inject.js` and `lokki.d.ts` are not touched.

- Every operator route behind the Host/Origin guard, the token gate and the operator check, in that order, and in `test_control.GUARDED`.
- Controls stay enabled and say `aria-busy` while their write or read runs, so a focused control keeps the focus; a press meanwhile does nothing, except on a mode control, where it waits and is sent next (spec 3.7, decision 21). A failed read says so in the error's words. An e2e step waits for `aria-busy` to clear before a second press.
- Every write is followed by a read; a control shows what the core reports, never the click (the mode slider shows a position held or stepped to until it is written, and a mode choice waiting behind a write is marked pending while the checked mark still follows the core: spec 1, 3.7).
- `ui/src/lib/mode.ts` is the home of the modes' words, `schema.py` of every setting's default, range, label and group, `activity.outcome()` of the run-record partition, `policy.REASONS` of the decision's reasons.
- The writable boundary (`writable`, `env_overrides`, the 409), the per-service restart flow, the stop sequence and the update banner's states are kept.
- No sentence says "free" or names a saving; a cut is cheaper than a finalized turn, never free (`docs/relay/cost-of-a-cut.md`).
- No new dependency.
- A flaky test gets its cause found before the merge.
- `--locked` on every Cargo command; commands in a gate chained with `&&`, no `| tail` hiding a status. Commit messages end with the session's attribution lines; `git add` names paths.
