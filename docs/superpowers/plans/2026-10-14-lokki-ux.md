# lokki Interface Redesign Implementation Plan

> **For agentic workers:** execute this plan task by task, in order, with the `superpowers:executing-plans` skill when the seat has the superpowers plugin, otherwise as written. Steps use checkbox (`- [ ]`) syntax for tracking. Each task is one pull request, branched off `lokki-ux` after the previous task's PR has merged; one PR at a time. Each task names its `Depends on`, its `Reopen when` (the premise whose failure sends the task back to the plan instead of being worked around), and its gate. No task's PR is red: every test a task adds passes in that task. A PR body carries one sentence per new test naming the behaviour that test binds and no existing test does (a behaviour an existing table can hold is a row there, not a new test), the test counts before and after that its gates printed, and, for a UI change, the screenshots in light and dark that decision 12 assigns to the task.

**The gates.** Each task's gate step names which of these it runs.
- **G-core** `cd core && python ci_quiet_suite.py`
- **G-ui** `cd ui && npm ci && npm run check && npm test && npm run e2e`
- **G-scripts** `cd app/scripts && python3 -m unittest`
- **G-inject** `cd app && node --test 'inject/*.test.mjs'`
- **G-rust** `cd app/src-tauri && cargo fmt --check && cargo clippy --locked --workspace -- -D warnings && cargo test --locked --workspace`, only in a task that changes something under `app/` (it cannot fail otherwise, and it costs a build on the shared host)
- **G-smoke** `cd app && bash smoke/smoke.sh`, in Tasks 3a (with the new `tauri.conf.json`, the shell still loads the page and the page reports `status=200 restart=ok`, its grants and its update state, which is what `smoke.sh` asserts), 6 (the panel hooks move) and 7 (the shell)

**Host rules** (every task, every command): ports 0 (`LOKKI_PORTS=0,0`; the e2e's `init --core-port 0 --cliproxy-port 0`), never `:8381`, `:8318` or `:1455`; for any Rust build (G-rust, G-smoke) a scratch `CARGO_TARGET_DIR` outside the checkout, `CARGO_BUILD_JOBS=4`, one Rust target at a time, 10 GB free on `/`, no build while a runner job is queued or running, and the target deleted after the gate; every other scratch outside the checkout, removed after; stop what you start by pid; `node_modules`, the UI build output and `__pycache__` removed before the PR is handed back.

**Goal:** The UI becomes four screens (Home, Accounts, Activity, Settings) around one mode control that is always visible with the decision it produces; the core serves what the run records hold through one new operator route, `GET /api/activity`, and three new fields on each `/api/schema` row; the tray offers the same three modes; and one seagull mark becomes the header mark, the favicon, the app icon and the tray icon. Nothing the core stores, decides or writes to a settings file changes.

**Architecture:** Two core PRs land first, so the UI has its contract before it is drawn. Task 1 puts each setting's label, group and choice labels in `schema.py` beside its meaning; the UI owns only the group titles and their order. Task 2 adds `core/lokki_core/activity.py`: under `core._runs_lock` it copies bytes from the end of the live run log and its rotated files until the copy reaches a line older than the window or 8 MiB, reading only each chunk's first line's `ts` with a byte search while it holds the lock; it releases the lock, parses and aggregates, and caches the aggregate for 10 s keyed on (window, live file size); one function, `outcome(record)`, makes both the class counts and each recent row's `outcome`; `routing.decide_now` appends each decision change to a bounded deque the route serves fresh. The UI PRs (Tasks 3a to 6) move the design tokens into `ui/src/app.css`, replace the four tabs with a sidebar of destinations and a top bar that carries the mode control and the decision line on every screen, and rebuild each view from the existing state module (`app`, `polled`, `saveSettings`: every write followed by a read). The mode control writes `routing` (and, for Auto, `low_quota.enabled: true` in the same body) and follows the read back, never its own click. The shell PR (Task 7) is the only Rust task besides Task 3a's one config key: the tray's three check items write the same bodies over HTTP with the token the shell already holds, the menu and the icon follow `/api/status` every 10 s, and the icon set is generated from the design's SVG files by one script. No page command, no dependency, no new store.

**Tech Stack:** what the tree already pins. Python 3.13 standard library and `unittest` for the core and the app scripts; Svelte 5.57, TypeScript 6.0, Vite 8.3, Vitest 5.0, `@testing-library/svelte` 5.4 with jsdom, `@playwright/test` 1.64 (Chromium) for the UI; Rust with `tauri` 2.12.3 (`tray-icon` feature: `CheckMenuItem`, `Menu::insert`/`remove`, `TrayIcon::set_icon_with_as_template`, `tauri::include_image!` for a PNG at compile time, `WebviewWindowBuilder::min_inner_size`, `App::primary_monitor`; all present in 2.12.3's source) for the shell; `@tauri-apps/cli` 2.12.2's `tauri icon` (already pinned in `app/package.json`) as the rasterizer for every icon. Charts and icons are inline SVG; the type is the system stack. No dependency is added (Global Constraints).

**Decisions the plan takes (where the spec left it open, or where the plan fills a gap the tree shows):**

1. **Below 720 px the sidebar folds into a row of tabs, the mode sentences collapse to one, and the shell's window has a minimum of 480 × 600.**
   - One `<nav aria-label="Destinations">`. At 720 px and wider it is the 208 px sidebar column. Below that, the layout grid places it directly under the top bar as one row of equal tabs (`flex: 1 1 0; min-width: 0`), each a 20 px icon over an 11 px (`--fs-xs`) label that ends in an ellipsis rather than wrapping (`white-space: nowrap; overflow: hidden; text-overflow: ellipsis`); the row never wraps and never scrolls. With five destinations (Task 5's interim state) each tab is 86 px wide at 480 px, and the longest label, "CLIProxyAPI", is about 66 px at 11 px. The sidebar's brand row and foot are hidden below 720 px (their facts are on Home and, from Task 6, in Settings › About).
   - The interim destinations: Tasks 3a to 5 carry "CLIProxyAPI" with the `external` icon (what remains in that view by then is opening the panel), and Task 5 adds "Activity" with the `activity` icon; Task 6 removes CLIProxyAPI.
   - The top bar wraps: the mode control on its own line; below 720 px, the full-size control (Home) shows only the checked mode's sentence under it, and the other two stay the radios' accessible descriptions, as in the compact control; then the decision line and the note.
   - Long values: a model or client name is one line, cut with an ellipsis, its full text in `title` and in the accessible name, in Activity's breakdowns and in the recent-runs table (where the model and client columns are at most 16 `ch`). The recent-runs table becomes a list of two-line rows (time · route · outcome; model · client · status · duration · tokens out) below **1000 px** of window, not 720 px: the table's eight columns need about 800 px of content, the content is the window less the 208 px sidebar, and at 1100 px the table was clipped; a media query is the tool, since container queries start at Safari 16 and the macOS floor is 12.4 (Safari 15.5). Every window under 720 px, with the sidebar folded, shows the list, and nothing in it scrolls sideways.
   - The minimum, `min_inner_size(480.0, 600.0)` (Task 7): 480 px holds the three mode segments and the longest unbreakable value on Home (`http://127.0.0.1:65535/v1` in the 13 px mono face, about 200 px) inside the 24 px padding. The height is 600, not 520: the folded chrome is about 300 px by the component sizes (top bar padding 32, control 40, one sentence 40, decision line up to 60, the note with its button up to 64, the gaps 24, the tab row 52), which leaves about 220 px of content at 520 and about 170 px when the update banner shows; 600 leaves about 300 px and 250 px. A plain browser has no minimum.
   - Proof, in the e2e at 480 × 600 on every screen the task has: the destinations are one row under the top bar and the brand is hidden; every visible element's `getBoundingClientRect().right <= innerWidth`, and every element whose computed `overflow-x` is `auto` or `scroll` has `scrollWidth <= clientWidth` (this sees inner scrollers, which the page's `scrollWidth` does not); and on Home with Auto and Low Quota Mode off (the note showing) the content scroller's `clientHeight >= 240`. If any of these fails at 480 × 600, the task is reopened and the number changes in this plan, not in the code.
2. **The tray icon is a template image on macOS, and on Windows and Linux it is drawn white unless the platform says the bar is light.** Windows reports the taskbar's theme in `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` as `SystemUsesLightTheme` (the taskbar and the tray; `AppsUseLightTheme` is the apps' theme, which differs on Windows 10's default of a dark taskbar with light apps); the shell reads it with `reg query … /v SystemUsesLightTheme` (no window, `creation_flags(0x0800_0000)`, as `sidecars.rs` runs `tasklist`), at start and on each 10 s refresh, and draws black on a light taskbar, white otherwise and when the read fails. Linux reports no panel colour: the freedesktop `color-scheme` setting is the applications' preference, and GNOME's top bar stays dark under a light preference, so a black icon chosen from it would vanish there; the icon is white, as the spec says for a platform that does not report. The sizes: on Windows and Linux the tray PNG is drawn at the pixel size the bar uses, `tray_px(os, scale)` = 16, 20, 24 or 32 for the primary monitor's scale factor 1, 1.25, 1.5 or 2 (the nearest). On Windows the taskbar draws its tray at 16 × that scale, so the 1.5 px line of the open form is drawn on the bar's own grid and never downsampled; on Linux the panel's indicator host picks its own icon size, and the size by scale is the best guess the shell can make. `primary_monitor()` is read on the refresh thread, never on the event loop; on macOS one 32 px template (the spec's @2x row). The choices are the pure `lokki_logic::tray::ink(os, light_bar)`, `tray_px(os, scale)` and `light_taskbar(text)`, tested by rows; the icon is set only when its form, ink or size changes, with `set_icon_with_as_template` (one call, no flicker between a non-template and a template render).
3. **The UI relies on `oklch()` with no fallback declarations; `color-mix()` stays out of the shipped CSS; the macOS floor is 12.4; the Linux build's WebKitGTK is checked before Task 3a merges.**
   - The engines: WebView2 (Chromium 111 and later, evergreen), the e2e's Chromium, WebKitGTK 2.52.6 on the Linux build host (the Linux build's glibc floor, 2.43, `README.md` "Linux", puts every system it runs on years past the first WebKitGTK that read `oklch()`; the AppImage carries the build host's WebKitGTK), and the system WKWebView on macOS.
   - macOS: the shipped UI uses `oklch()` (Safari 15.4) and `inert` (Safari 15.5), so `bundle.macOS.minimumSystemVersion` is `"12.4"`, the first macOS whose system WebKit has both built in (the facts above). macOS 10.15 and 11 with Safari 15.5 installed would also work, but the OS version is what the bundle can check. `color-mix()` (Safari 16.2) is kept out of the shipped CSS: the prototypes' `color-mix(in oklch, …)` hover fills become tokens with literal `oklch()` values, light and dark. `README.md` states the floor beside the Linux one.
   - An engine that does not read a token's colour drops it and falls back to the inherited system text colour on a transparent ground (the fact above): the page stays legible, and every state keeps its word or its icon (spec 7). The mode control's checked segment carries a check icon and semibold weight besides its fill, so the chosen mode does not rest on colour.
   - The build target backs the floor: Task 3a sets `build.target` (and so `build.cssTarget`, which follows it) in `ui/vite.config.ts` to `["safari15.5", "chrome111"]`, the engines the floor names (WKWebView of macOS 12.4 and WebView2 at its `oklch()` floor). Vite's default in the pinned line is `safari16.4`, which leaves syntax from Safari 15.6 to 16.4 unlowered: a SyntaxError and a blank window on a 12.4 WebView. The target lowers syntax (static blocks and private fields, for instance); it does not lower a regular expression the bundle builds (a lookbehind, `(?<=` and `(?<!`, is Safari 16.4; the `v` flag is Safari 17), which passes through as `new RegExp(...)` and builds silently, and it cannot see a runtime API newer than 15.5. Step 9's scan of the built bundle is the cheap guard for the regular expressions. WebKitGTK needs no entry of its own, and loading the bundle in its 2.52.6 (Step 9) catches a bundle broken on a newer engine; it cannot show compatibility with 15.5, which is far older. No Safari 15.5 engine is available here, so 15.5 compatibility beyond the lowered syntax and the scan is unproven, and Task 3a's PR body says so.
   - The check (Task 3a, Step 9): every colour function in the built stylesheet is read by the Linux build host's WebKitGTK; its output, with the version, goes in the PR body.
4. **`p50` and `p90` are nearest-rank percentiles of `elapsed_s`.** For the `n` values of a route sorted ascending, the `p`-th percentile is the value at 1-based rank `-(-p * n // 100)` (the ceiling of `p·n/100` in integers); `null` when `n` is 0; a record without a numeric `elapsed_s` counts in no latency. Nearest rank always answers a duration a run actually took (the UI draws "solid to p50, outline to p90" of real runs), needs no interpolation choice and agrees with the usual definition at small `n`. `activity.percentile(values, p)` is the one home; `test_latency_is_the_nearest_rank_p50_and_p90_per_route_and_overall` pins it with rows that interpolation would fail: `[1 … 10]` gives p50 `5` and p90 `9` (linear interpolation and `statistics.median` answer `5.5` and `9.1`), `[1, 2, 3, 4]` gives `2` and `4`, `[7.5]` gives `7.5` and `7.5`, `[]` gives `null`.
5. **Every time in `/api/activity`'s answer is integer epoch seconds:** `now`, `from`, `buckets[].start`, `coverage.oldest`, `recent[].ts` and `events[].at`. The spec writes `oldest` and `recent.ts` as "the ts" of a record; the record's ISO string is converted by the one `ts` parser (decision 17), so the UI formats one kind of time. `now` is `int(time.time())`; a record with `from <= ts <= now` is in the window, and one at exactly `now` falls in the last bucket. The UI formats every time with `clock`, 24-hour `HH:MM` in local time (`hourCycle: "h23"`), and parses `Status.started_at` (an ISO string) before it.
6. **Field shapes the spec named without fixing:** `choice_labels` is an object from each choice to its label (`{"all": "every watched account is low", "any": "any watched account is low"}`), `{}` on a row with no choices; `group` is one of `schema.GROUPS` = `saving`, `connection`, `cliproxy`, `tuning.cutting`, `tuning.tool_calls`, `tuning.traffic`, `tuning.quota_reading`, `file`, `hidden` (`auth.*`, never shown, as today). A null `model` or `client` counts under `"unknown"` in `models` and `clients`; a record whose `route` is none of the three counts in `coverage.records` and nowhere else; ties in the top-8 order break by name.
